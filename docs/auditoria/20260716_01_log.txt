1. Resolução de Autenticação e Regras do Supabase
Sintoma: Falhas no registro e login na interface B2B, retornando erros HTTP 400 (Bad Request), 422 (Unprocessable Content) e, por fim, o código email_provider_disabled.

Causa Raiz:

O provedor de e-mail e senha havia sido desativado globalmente nas configurações do Supabase.

O Supabase impõe validações rigorosas pré-banco (ex: senhas com mínimo de 6 caracteres e rejeição de e-mails com espaços invisíveis finais).

Ação Corretiva: Reativação da chave "Enable Email provider" no painel Authentication > Providers do Supabase. Padronização das credenciais de teste para respeitar os limites de segurança da API.

2. Governança de Acesso e Roteamento Zero Trust
Sintoma: O usuário com credenciais de Profissional não conseguia visualizar o menu clínico, sendo redirecionado compulsoriamente para o painel de Administração (/admin).

Causa Raiz: O usuário de teste estava configurado como um "Super Usuário" (is_admin = true E eh_profissional = true). O React Router foi programado com base no Princípio do Menor Privilégio: se a conta for Admin, ela é travada no painel de gestão para evitar que gestores tenham acesso a dados clínicos de pacientes (Blast Radius). Além disso, o acesso clínico exigia que a flag status_aprovacao estivesse estritamente como 'aprovado'.

Ação Corretiva: Validação de que a trava de segurança atua conforme exigido pela LGPD/HIPAA. Estabelecimento da diretriz de testes utilizando duas contas segregadas em vez de contas híbridas, garantindo a separação de responsabilidades. Ajuste manual do status_aprovacao via banco.

3. Estratégia de Semeadura de Dados (Seed) em Ambiente Cloud
Sintoma: Erro ERROR: 42501: must be owner of table users ao tentar executar o script seed.sql diretamente no SQL Editor do Supabase hospedado.

Causa Raiz: Bloqueio de segurança arquitetural do Supabase. A tabela auth.users é gerenciada exclusivamente pela role supabase_auth_admin. Usuários normais (mesmo o administrador do projeto usando o SQL Editor) não têm privilégios para executar INSERT, DROP ou TRUNCATE diretamente nessa tabela na nuvem.

Ação Corretiva (Migração de Estratégia):

Abandono do uso do arquivo seed.sql puro para o ambiente em nuvem (mantido apenas para resets locais via Docker).

Desenvolvimento de um script em Node.js/TypeScript (scripts/seed_cloud.ts).

Utilização da Admin API do Supabase através da Service Role Key (chave mestra injetada via variável de ambiente .env temporária) para criar 10 pacientes fictícios e gravar 6 meses de histórico clínico contornando as restrições de forma segura e automatizada.

4. Sincronia de Branches e Servidor de Desenvolvimento
Sintoma: As atualizações de interface (como a correção do menu mobile) não refletiam no navegador local, mesmo após o commit ser confirmado pelo Claude.

Causa Raiz: O terminal executando o servidor do Vite (npm run dev) ficou dessincronizado em relação à árvore do Git (preso na branch antiga).

Ação Corretiva: Parada do servidor local (Ctrl+C), execução de git checkout para a branch correta e limpeza de cache do navegador (Hard Refresh).

1. Governança de Acesso e Roteamento "Zero Trust" (SecOps)
Desafio: O React Router precisava refletir com exatidão a separação de papéis na plataforma para evitar acessos indevidos a dados de saúde (LGPD/HIPAA).

Sintoma: Usuários de teste configurados como "Super Usuários" (is_admin = true e eh_profissional = true) eram barrados da área clínica.

Resolução: Validação da arquitetura de menor privilégio. O sistema foi intencionalmente programado para priorizar o bloqueio administrativo (Blast Radius). Se a conta for Admin, ela fica presa no painel de gestão para evitar que gestores leiam dados de pacientes. Estabeleceu-se a obrigatoriedade de testes com contas segregadas e a exigência estrita do campo status_aprovacao = 'aprovado' no banco de dados para liberar a interface de consultas.

2. Autenticação e Configuração do Provedor (Supabase Auth)
Desafio: Falhas de login no ambiente web retornando HTTP 422 (Unprocessable Content).

Causa Raiz: O serviço de autenticação por e-mail estava com a chave email_provider_disabled ativa nas configurações do projeto na nuvem, bloqueando qualquer tentativa de entrada por e-mail e senha.

Resolução: Reativação manual do Email Provider no painel do Supabase. Também foi documentada a sensibilidade da API a espaços em branco invisíveis no input de e-mail e limites mínimos de senha.

3. Criptografia e Proteção de Dados Pessoais (PII)
Desafio: Como popular dados de pacientes (Nomes e E-mails) no banco de testes sem quebrar a aplicação.

Decisão Arquitetural: O Claude Code identificou que a tabela perfis_usuarios utiliza criptografia de ponta a ponta (AES-256-GCM) no lado do cliente. Escrever texto plano (Plaintext) nessa tabela via SQL faria o frontend React quebrar ao tentar descriptografar. Os dados fictícios foram alocados nos metadados da tabela auth.users para simular a arquitetura real de segurança, garantindo que PII (Informação Pessoalmente Identificável) não fique exposta.

4. Estratégia de Semeadura de Dados (Database Seeding) - Local vs Nuvem
Desafio: O script seed.sql falhou ao ser executado no Supabase Cloud com o erro ERROR: 42501: must be owner of table users.

Causa Raiz: Restrição nativa de segurança do Supabase. A tabela auth.users é propriedade do papel supabase_auth_admin. Comandos diretos de INSERT, TRUNCATE ou DELETE são bloqueados via SQL Editor no ambiente em nuvem.

Resolução:

Local (Docker): O seed.sql foi preservado exclusivamente para o comando supabase db reset.

Nuvem (Cloud): Criação do utilitário scripts/seed_cloud.ts (Node.js/TypeScript). Este script utiliza a Admin API e a Service Role Key para injetar 10 pacientes fictícios e 6 meses de métricas diárias, garantindo idempotência (sem duplicação de dados).

5. Gestão de Variáveis de Ambiente e Segurança de Chaves
Desafio: Proteger a Service Role Key (Chave Mestra) de vazamentos no repositório.

Resolução: O arquivo .env.example foi atualizado para conter apenas placeholders. A chave mestra foi isolada em uma variável estrita de backend (SUPABASE_SERVICE_ROLE_KEY), sem o prefixo VITE_, garantindo que ela jamais seja exposta no pacote do frontend (build).

6. Fluxo de Trabalho Git (Stacked Branches) e Ambiente de Desenvolvimento (DX)
Desafio: Gerenciar código em desenvolvimento progressivo sem poluir a branch principal (main) e lidar com falhas de sincronia de cache local (UI mobile não refletindo no navegador do usuário).

Resolução:

Git Flow: Adoção do modelo de Stacked Branches (Branches empilhadas). A correção de layout (fix/sidebar-responsiveness) foi apontada para sofrer merge em sua branch pai (feat/layout-and-seed-data), em vez de ser enviada isoladamente para a main, evitando "Git Hell" e preservando a integridade das 13 atualizações acumuladas.

Developer Experience (DX): Padronização de comandos para testes de UI (git checkout, npm run dev, Hard Refresh do Vite).

Testes Automatizados: Utilização de ferramentas Headless (Playwright) pelo agente autônomo para validação visual (375px e 1280px) simulando o DOM real sem depender apenas da leitura de código.
