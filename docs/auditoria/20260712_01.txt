1. Auditoria de Segurança

🟢 Boas notícias

- Nenhuma chave real foi encontrada no código. Vasculhei tudo à procura de padrões de chaves Google/Supabase/senhas hardcoded. O .env está vazio (0 bytes) e nunca foi enviado ao Git (confirmei no histórico completo). O .env.example e o web_painel/.env.example só têm textos de exemplo tipo your-anon-key-here.
- O .gitignore está bem configurado: bloqueia .env, as pastas temporárias do Supabase CLI (supabase/.temp/, supabase/.branches/) e o .env do painel web.
- As chaves realmente sensíveis (a "chave mestra" do Supabase e as credenciais da Garmin) só existem como variáveis de ambiente do lado do servidor (Deno.env.get(...) dentro da Edge Function garmin-gateway) — nunca aparecem no código. Isto é exatamente o padrão certo.
- O app mobile também está bem desenhado: se alguém esquecer de configurar as credenciais do Supabase, o app recusa-se a arrancar em vez de rodar silenciosamente contra um projeto inexistente. Isto é uma boa prática de "falha segura".

🟡 Pontos de atenção (não são "chaves roubadas", mas merecem revisão humana antes de lançar)

1. E-mail dos utilizadores guardado sem cifra. O documento mestre exige "criptografia em repouso" para a tabela perfis_usuarios (dado de sigilo máximo). Na prática, nome e telefone já saem do telemóvel cifrados (AES-256) antes de chegarem à base de dados — mas o e-mail vai em texto simples. Isto está confirmado no próprio comentário de uma das migrações SQL. É uma discrepância entre o que o documento promete e o que o código faz.
2. Tokens da Garmin (OAuth) guardados em texto simples na base de dados. A decisão está documentada e tem justificação razoável (só a "chave mestra" do servidor consegue ler essa linha, nunca o telemóvel do utilizador), mas como envolve um segredo de terceiros, vale a pena um segundo par de olhos antes do lançamento.
3. O código do "Motor de Sinistralidade" (item proibido, EM HOLD) ainda está no teu computador, em 3 ficheiros que não foram enviados ao Git — o que é bom, ninguém os "commitou" por engano. Confirmei também que nenhuma outra parte do app importa ou usa esses ficheiros — não há botão, ecrã ou rota que leve até eles. Porém, não existe um "interruptor" (feature flag) explícito a bloqueá-los, como o protocolo pede — hoje eles só estão isolados "por ninguém lhes tocar", o que é frágil se um futuro assistente de IA decidir ligá-los sem perceber que são proibidos.

Conclusão de segurança: não há vazamento de segredos ativo. O maior risco real hoje é de processo (chaves proibidas sentadas na tua pasta de trabalho, prontas a ser commitadas por engano) e não de exposição.

2. Estado das políticas RLS (quem pode ver os dados de quem)

RLS é a trava que impede um utilizador de ler os dados de outro diretamente pela API. Boas notícias aqui também:

- Todas as 13 tabelas existentes têm RLS ativado, cada uma com uma política que só permite ao próprio dono (auth.uid()) ler/escrever a sua linha. Não encontrei nenhuma tabela desprotegida.
- O painel web dos profissionais (nutricionistas/médicos) está bem desenhado: um profissional só vê os dados de um paciente se já existir uma prescrição registada ligando os dois (planejamento_clinico). Não há "profissional vê tudo" — é sempre escopado a uma relação real já existente na base de dados. Isto é o padrão "Zero Trust" que o documento pede.
- Existe até uma "view" especial (perfis_pacientes_vinculados) desenhada só para não vazar o e-mail/telefone do paciente ao profissional, mesmo que ele tenha acesso aos dados de saúde. Bom detalhe de engenharia.

Pontos a resolver

- metricas_saude (tabela antiga) ficou órfã no banco: foi substituída por 5 tabelas mais específicas numa migração posterior, mas nunca foi apagada, e nenhum código a usa hoje. Tem RLS correto (não é insegura), mas é "peso morto" — vale limpar.
- ciclo_menstrual existe no banco com RLS correto, mas não aparece em nenhum dos dois documentos mestres nem é usada por nenhum ecrã do app. Ou foi esquecida na documentação, ou é código morto — precisa de decisão.
- Não existe nenhuma política de "apagar" (DELETE) em nenhuma tabela. Isto é seguro por padrão (ninguém consegue apagar dados pela API pública), mas significa que quando implementares a exportação/exclusão de dados (F16, exigência da lei LGPD), vais precisar de um caminho especial passando pela "chave mestra" do servidor.
- Não consegui fazer o teste prático "2 utilizadores tentam ler dados um do outro" porque isso exigiria criar utilizadores de teste reais no Supabase — é uma auditoria só de leitura de código. Recomendo como próximo passo prático.
