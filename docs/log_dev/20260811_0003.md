## 1. Mapeamento do Painel Web — achado principal

**O painel administrativo NÃO é Flutter Web.** É um projeto **React + TypeScript + Vite** completamente separado, na pasta `web_painel/` na raiz do repositório — sem `pubspec.yaml`, sem nenhuma dependência do Flutter. Confirmei isso listando o diretório: `web_painel/package.json` declara `react`, `react-router-dom`, `@supabase/supabase-js`, `recharts`, `lucide-react`, TailwindCSS — nenhum pacote Flutter/Dart em lugar nenhum.

Isso bate exatamente com a Diretriz do Fundador ("o assistente de IA se perdeu ao tentar deduzir a arquitetura") — a suposição mais natural (Flutter Web dentro de `lib/`, com roteamento responsivo) está **errada**. A app mobile (Flutter, este repositório na raiz `lib/`) e o painel web (React, `web_painel/`) são dois codebases irmãos que conversam com o MESMO projeto Supabase, cada um com seu próprio cliente (`Supabase.instance.client` no Flutter, `createClient<Database>()` em `web_painel/src/core/supabase.ts`).

### Estrutura de `web_painel/`

```
web_painel/
  src/
    App.tsx                              — roteamento (react-router-dom) + gate de autenticação
    core/
      supabase.ts                        — cliente Supabase + login/RBAC/D2
      types/database.ts                  — tipos do schema, escritos à mão (sem CLI do Supabase disponível)
    components/
      LoginPage.tsx / UpdatePasswordPage.tsx / Toast.tsx
      layout/DashboardLayout.tsx, Sidebar.tsx, PlaceholderPage.tsx
    features/
      admin/components/AdminOverview.tsx, AdminDashboard.tsx    — backoffice ("Sala de Espera")
      dashboard/components/Dashboard.tsx, PatientDetails.tsx    — home do profissional
      patients/components/PatientList.tsx, InvitePatientModal.tsx, services/vinculosApi.ts
      prescriptions/components/GarminPrescriptionForm.tsx, services/garminApi.ts
  scripts/                                — ETL/seed (TACO, embeddings) — nada a ver com N06
```

Não há biblioteca de formulários (react-hook-form/Formik) nem de data-fetching (react-query/SWR) — todo o estado é `useState`/`useEffect` + chamada direta ao `supabase-js`. Qualquer tela nova do N06 deve seguir esse MESMO padrão manual para não introduzir uma dependência nova sem essa decisão ser explícita.

### Controle de acesso hoje — RBAC real

**Não existe uma tabela de papéis/permissões granular.** O controle é feito por **duas colunas booleanas em `perfis_usuarios`** (`is_admin`, `eh_profissional`) + o enum `tipo_profissional` (`Medico`/`Nutricionista`/`Fisioterapeuta`/`Personal_Trainer`/`Auditoria_Seguradora`) + o enum `status_aprovacao` (`pendente`/`aprovado`/`rejeitado`).

- **No banco (a barreira real)**: função SQL `eh_admin()` (`20260714100000_add_approval_workflow.sql`) lê `is_admin` da PRÓPRIA linha do chamador (`auth.uid()`), usada nas policies `perfis_usuarios_select_admin`/`perfis_usuarios_update_admin` para liberar um admin ler/escrever QUALQUER linha (não só a própria). Um trigger (`perfis_usuarios_bloquear_auto_promocao`, citado em comentário) impede que o próprio usuário se autopromova a admin.
- **No cliente (só UX, documentado explicitamente no código-fonte)**: `App.tsx` esconde rotas (`/admin`, `/admin/aprovacoes`) atrás de `profissional.isAdmin`, e `Sidebar.tsx` só renderiza a seção "Administração" para quem tem essa flag. O comentário em `App.tsx` é explícito: *"este `Navigate` é só uma conveniência de UX, nunca a barreira real"* — a real é a RLS.
- **Login profissional** (`signInProfissional`, `core/supabase.ts`): exige `is_admin = true` OU (`eh_profissional = true` E `tipo_profissional` preenchido) E `status_aprovacao = 'aprovado'`. Uma conta com senha certa mas sem essas condições é deslogada (`signOut`) antes do erro ser lançado — nunca fica "meio autenticada" no `localStorage`.

**Para o N06**: telas novas de manutenção (usuário, profissional, atividades físicas, alergias, alimentos, configurações) devem seguir o MESMO padrão: uma policy RLS `..._select_admin`/`..._update_admin`/`..._insert_admin` usando `eh_admin()`, mais um item de rota/Sidebar escondido por `profissional.isAdmin` (só UX). Não há necessidade de criar um sistema de roles novo — o binário admin/não-admin já cobre o caso de uso descrito.

## 2. Auditoria de Criptografia (D2)

### Extensão usada: **pgcrypto**, não pgsodium

O Documento Mestre/prompt do N06 supõe `pgsodium` como possibilidade — **não é o que está implementado**. A migration `20260730160000_d2_pii_criptografia_repouso.sql` usa:

- **`pgcrypto`** (`pgp_sym_encrypt`/`pgp_sym_decrypt`, AES-256, formato PGP simétrico) + `armor()`/`dearmor()` para manter as colunas como `text` legível-ASCII (`-----BEGIN PGP MESSAGE-----...`).
- **`supabase_vault`** (extensão `supabase_vault`, schema `vault`) guarda a chave simétrica de 256 bits — gerada aleatoriamente NO BANCO na primeira execução da migration (`vault.create_secret`), nunca hardcoded em nenhum arquivo. Só funções `SECURITY DEFINER` conseguem ler `vault.decrypted_secrets`.

### Como funciona hoje, ponta a ponta

1. **Escrita**: um trigger `before insert or update` em `perfis_usuarios` (`private.tg_perfis_usuarios_cifrar_pii`) cifra `nome`/`telefone`/`email` transparentemente — nenhum cliente (app mobile, painel web, seeds) precisa saber que a cifra existe; todos continuam mandando texto plano. No UPDATE, só recifra o campo que de fato mudou (`new.x is distinct from old.x`), preservando o ciphertext dos campos não tocados.
2. **Leitura do próprio dono**: RPC `public.meu_perfil_seguro()` (`SECURITY DEFINER`, `search_path=''`, escopada a `auth.uid()`) devolve a própria linha com `nome`/`telefone`/`email` já decifrados. É o que `web_painel/src/core/supabase.ts` chama hoje (`buscarPerfilBruto`) e o que o app mobile usaria de forma equivalente.
3. **Leitura de OUTRA pessoa (o que falta para o N06)**: o comentário da própria migration documenta a lacuna — *"a decifra do nome de um paciente por um profissional com vínculo ativo é uma capacidade que a infra de D2 já suporta (Parte 7.4), mas que NÃO foi ligada aqui de propósito"*. Busquei por "Parte 7.4"/qualquer RPC de decifra escopada a vínculo profissional-paciente em todas as migrations — **não existe ainda**. Só a auto-decifra (`meu_perfil_seguro`) está implementada.

### Achado real, não hipotético: `AdminDashboard.tsx` está lendo ciphertext hoje

Fui conferir se as telas administrativas já existentes lidam com essa cifra corretamente. **Não lidam.** `AdminDashboard.tsx` (a "Sala de Espera", tela de aprovação de profissionais) faz:

```ts
supabase.from('perfis_usuarios').select('id, nome, email, tipo_profissional, criado_em')...
```

Um `select` direto na tabela-base — que, desde o D2, devolve `nome`/`email` como bloco PGP ilegível, não texto plano. Confirmei pela data: `AdminDashboard.tsx` foi commitado em 14/07 (`git log`), a migration D2 é de 30/07 — a tela nunca foi atualizada depois da cifra entrar em produção. **Hoje, a coluna "Nome"/"E-mail" na Sala de Espera provavelmente mostra o bloco `-----BEGIN PGP MESSAGE-----...` em vez do nome real do profissional solicitando acesso.** Isso não é uma suposição da tarefa anterior — é uma consequência direta e verificável da ordem cronológica das duas migrations/commits.

Isso é exatamente o gap que a RPC de decifra do N06 precisa fechar — e não só para as telas NOVAS, mas para consertar essa que já existe.

## 3. Plano de Arquitetura para o N06

### 3.1 Migrations necessárias (Supabase)

1. **`alergias`** (catálogo) — nova tabela, mesmo espírito de `tipos_atividades_fisicas`: `id`, `nome_codigo`, `nome_exibicao`, RLS de leitura pública a `authenticated`, escrita só admin (`eh_admin()`).
2. **`usuario_alergias`** (relação usuário↔alergia, N:N) — não pedida explicitamente no prompt, mas necessária se o objetivo é o usuário FINAL declarar alergias, não só o painel administrar o catálogo. **Decisão do fundador necessária**: confirmar se "manutenção de alergias" é (a) só o catálogo global de alergias conhecidas, ou (b) também a associação usuário×alergia.
3. **`configuracoes`** — schema totalmente em aberto; nenhuma pista no código sobre o que essa tela deveria configurar (preferências de notificação? feature flags? parâmetros do Motor Clínico?). **Bloqueante**: preciso de uma definição do fundador antes de desenhar as colunas.
4. **RPCs de decifra "para admin"** (o item central de D2 do N06):
   - `admin_listar_perfis_pendentes_seguro()` (ou nome equivalente) — mesmo padrão SECURITY DEFINER de `meu_perfil_seguro()`, mas: (a) gated por `eh_admin()` internamente (não por `auth.uid() = id`), (b) devolve MÚLTIPLAS linhas decifradas, filtradas por `status_aprovacao = 'pendente'` — substitui o `select` direto quebrado do `AdminDashboard.tsx` atual.
   - Uma RPC equivalente e mais genérica para a manutenção de "usuário"/"profissional" do N06 (provavelmente paginada, com filtro), já que a tela de manutenção vai precisar listar e decifrar N perfis de uma vez, não só os pendentes.
   - Escrita (`UPDATE`/`INSERT` em `nome`/`telefone`/`email` a partir do painel) já funciona hoje sem RPC nova — o trigger de cifra intercepta transparentemente qualquer `UPDATE` feito por um admin (a policy `perfis_usuarios_update_admin` já libera isso). Só a LEITURA multi-linha decifrada precisa de RPC nova.
5. **Tela de manutenção de "profissional × usuário"**: como `vinculos_profissional_paciente` já tem `Insert: never`/`Update: never` no `database.ts` (só RPC, ainda não implementada no lado de escrita), confirmar se já existe uma RPC de criação/edição de vínculo em alguma Edge Function ou se o N06 também precisa criá-la — não encontrei nenhuma neste spike (fora do escopo desta leitura: não auditei `supabase/functions/`).
