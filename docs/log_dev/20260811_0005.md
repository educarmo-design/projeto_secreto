## PARTE 1 — N03 (maioridade 18+) nas três pontas

- Migration `20260811190000_n03_trava_maioridade.sql`:
  - CHECK constraint `perfis_usuarios_maioridade` em `perfis_usuarios`
    (`NOT VALID` — só valida escritas novas, não força re-validação em
    massa de linhas existentes, mesmo padrão já usado em
    `20260713100000_estruturas_b2b_v4.sql`): `data_nascimento is null or
    data_nascimento <= current_date - interval '18 years'`.
  - Função `public.calcular_idade(p_data_nascimento date) returns int
    language sql stable` — **não é coluna gerada** porque
    `GENERATED ALWAYS AS (...) STORED` exige expressão IMMUTABLE, e
    `CURRENT_DATE`/`age()` são STABLE, não IMMUTABLE. Documentado em
    comentário na migration.
- Painel Web (`LoginPage.tsx`): campo "Data de nascimento" no formulário
  de solicitação de acesso, com `calcularIdade()` (mesma aritmética de
  anos completos, não só subtração de ano) bloqueando o `handleSubmit`
  antes de chamar `solicitarAcesso` se `< 18`.
- App Flutter (`perfil_usuario_page.dart`): campo de data de nascimento
  (seletor via `showDatePicker`, sem `TextFormField` de texto livre) na
  tela de Perfil; `_idadeEmAnos()` replica a mesma aritmética; `_salvar()`
  bloqueia localmente sob 18 anos E trata `PostgrestException` da CHECK
  constraint com a mesma mensagem amigável (Zero Trust: a barreira real é
  o banco, a validação client-side é só UX).
- `perfil_usuario_repository.dart`: `buscarDataNascimento()`/
  `atualizarDataNascimento()` novos, mesmo padrão de
  `buscarAlturaCm()`/`atualizarAlturaCm()` (inclusive a convenção
  `null` = "ninguém logado" OU "coluna vazia").

## PARTE 2 — D3: Matriz de Permissões Dinâmica (RBAC M:N)

Correção explícita do fundador preservada: nenhum artefato `.md` estático —
estrutura 100% dinâmica no banco com tela de gestão em tempo real.

- Migration `20260811200000_d3_rbac_dinamico.sql`:
  - Tabelas `papeis`, `permissoes`, `papeis_permissoes` (M:N
    papel↔permissão), `usuario_papeis` (M:N usuário↔papel) — **aditivas**,
    coexistindo com o gate binário pré-existente
    (`is_admin`/`eh_profissional`/`tipo_profissional`), não o substituindo.
  - Seed: 6 papéis (admin, medico, nutricionista, personal,
    fisioterapeuta, atleta) e ~22 permissões por módulo (usuarios,
    profissionais, vinculos, atividades_fisicas, alergias, alimentos,
    configuracoes, telemetria, permissoes).
  - Backfill idempotente: usuários `is_admin=true` → papel `admin`;
    `eh_profissional=true AND status_aprovacao='aprovado'` → papel
    correspondente ao `tipo_profissional`.
  - RPC `tem_permissao(p_usuario_id, p_permissao_codigo)` — leitura.
  - RPC `admin_atualizar_permissao_papel(p_papel_id, p_permissao_id,
    p_habilitado)` `security definer`, valida `eh_admin()` no servidor e
    é a **única porta de escrita** da matriz: `papeis_permissoes` não tem
    nenhuma policy de INSERT/DELETE nem GRANT de escrita para
    `authenticated` — defesa em profundidade, não só RLS.
- React `AdminMatrizPermissoes.tsx` (nova): tabela com permissões
  agrupadas por módulo (linhas) × papéis (colunas), cada célula um
  checkbox; toggle otimista chamando a RPC acima, reversão automática se
  o servidor recusar. Roteada em `/admin/permissoes` (`App.tsx` +
  `Sidebar.tsx`).
