# 20260811_0002 — Treinos, Rotas GPS, FC por intervalo e Calorias Granulares

- **Tarefa**: engenharia de dados e fluxo completo multiplataforma (migrations, repositórios, lógica de negócio) para Sincronização de Treinos, Rotas, FC de Treino e Calorias Granulares.
- **Branch**: `feature/n17-n18-telemetria-persistida`.

## Migrations (`20260811160000_atividades_fisicas_calorias_granulares.sql`)

- `metricas_saude_diarias`: `calorias_basais`/`calorias_totais` novas (`calorias_ativas` já existia desde a Onda 1.5).
- `tipos_atividades_fisicas` (dicionário): `nome_codigo` espelha `HealthWorkoutActivityType.name` do pacote `health` exatamente — sem camada de tradução. Populado via `INSERT` com os 43 códigos da seção "Both" (comuns Android+iOS) do enum, mapeado no spike da tarefa anterior (RELATÓRIO 20260810_0007). RLS: select liberado a todo autenticado (catálogo público de leitura).
- `atividades_fisicas_treinos`: `id uuid` (não bigserial — precisa existir ANTES do insert pra virar FK de rotas sem uma segunda ida ao banco). `unique(usuario_id, inicio_atividade)` para idempotência. RLS de dono (select/insert/update).
- `atividades_fisicas_rotas`: só os campos comuns Android/iOS pedidos (`latitude`, `longitude`, `timestamp_ponto`, `altitude`, `precisao`) — sem coluna `usuario_id` própria, por desenho; RLS via `exists` contra `atividades_fisicas_treinos` (mesmo princípio de `perfis_pacientes_vinculados`, 20260713140000): a posse é sempre a do treino pai.
- Aplicada com sucesso via `npx supabase db push`.

## Lógica de sincronização (`HealthSyncService`)

- `HealthMetricPoint` ganha `rawValue` (o `HealthValue` cru, não achatado) — `WORKOUT`/`WORKOUT_ROUTE` carregam `WorkoutHealthValue`/`WorkoutRouteHealthValue`, que o achatamento numérico existente (`value: double`) descartava por completo.
- `todosOsTipos`: `BASAL_ENERGY_BURNED` e `WORKOUT_ROUTE` adicionados.
- `_mesclarPorDia`: `calorias_basais` com o mesmo tratamento anti-double-counting (maior fonte) de `calorias_ativas`; `calorias_totais` = ativas+basais (soma tratando o ausente como 0, só quando pelo menos uma existe naquele dia) — não é `TOTAL_CALORIES_BURNED` (achado da tarefa anterior: sem implementação real no lado iOS do pacote `health`).
- Novo `_processarTreinos` (chamado em `_lerEGravar`, sobre `leitura.points` cru — nunca sobre `payloads`, já que WORKOUT/WORKOUT_ROUTE não mapeiam a nenhum campo de `HealthPayloadModel`):
  - **FC do treino**: filtra o array de HEART_RATE bruto do lote inteiro (pode cobrir vários dias) pelas leituras cujo `[dateFrom, dateTo]` cai dentro do `[dateFrom, dateTo]` daquele WORKOUT específico — calcula média/mín/máx só com essas. Nenhuma lógica de anomalia/evento (restrição F02, RELATÓRIO 20260810_0004 preservada).
  - Upsert do treino com `onConflict: 'usuario_id,inicio_atividade'` — idempotência.
  - **Rota**: `_gravarRotaDoTreino` associa a rota ao treino pelo mesmo critério de intervalo de tempo (contenção), apaga rotas antigas do treino e insere as novas (idempotência "limpa e reinsere", pedido explícito da tarefa).
  - Best-effort do início ao fim (mesmo espírito de `_detectarEregistrarAnomalias`): falha em um treino/rota é logada e o loop segue; nunca derruba a sincronização principal de `metricas_saude_diarias`.

## Permissões nativas

- **Android**: `READ_BASAL_METABOLIC_RATE` adicionada (confirmado via bytecode do `androidx.health.connect:connect-client` — `BASAL_ENERGY_BURNED` mapeia para `BasalMetabolicRateRecord`). **Achado real**: `WORKOUT_ROUTE` NÃO precisa de permissão nova — lendo `HealthDataOperations.kt` do pacote `health`, o plugin só pede `READ_EXERCISE` (a mesma de `WORKOUT`) pra leitura de rota; `READ_EXERCISE_ROUTES` existe como constante na biblioteca mas nunca é usada pra READ. O acesso à rota em si é um consentimento à parte, por sessão, pedido em tempo de execução pelo próprio Health Connect — não algo que se declare no Manifest.
- **iOS**: texto de `NSHealthShareUsageDescription` revisado para mencionar explicitamente rota/localização durante o treino — não precisa de `NSLocationWhenInUseUsageDescription` à parte, já que `WORKOUT_ROUTE` (HKWorkoutRoute) é lido via HealthKit, não CoreLocation.
