## Correção de fato (investigado antes de presumir, Parte 0)

O Mestre v7.0 registra `alimentos_referencia` com **~8.000 itens** e **23**
com embedding mock. Consultando o banco real (não presumindo o número do
documento):

- **Total real: 637 linhas** — não ~8.000. `scripts/etl_carga_taco.ts` (596
  itens TACO) e `scripts/seed_taco_completa.ts` (100+ itens, idempotente por
  nome) já tinham sido rodados numa sessão anterior; a diferença para 637 vem
  da soma dessas cargas com o seed original de 5 + 3 de teste, descontando
  nomes duplicados que a idempotência por nome pulou. **Nenhuma carga de
  dados nova foi necessária nesta tarefa** — a TACO completa já estava
  carregada; o trabalho era só re-embeddar o que já existe.
- **Todas as 637 linhas já tinham `embedding` não-nulo** — não "23 mock, o
  resto vazio". Não dá pra distinguir mock de real olhando só o vetor (testei
  a norma L2 de uma amostra: um mock pode sair normalizado igual a um real).
  Por isso a solução não foi "achar os 23" — foi tratar TODAS as linhas como
  "proveniência desconhecida" e re-semear por igual (ver decisão técnica #1).

Isto não é uma falha da tarefa — é o tipo de "correção de fatos" que o
próprio Mestre v7.0 já pratica na sua seção 2.3 (C1–C6). Atualizar o Mestre
com este número fica fora do escopo desta tarefa (não sou eu quem edita os 3
prompts sincronizados — Parte 0 regra 19), mas fica registrado aqui para
quem for revisar o documento.

## Decisões técnicas | motivo

1. **Coluna nova `alimentos_referencia.embedding_model` (proveniência) em vez
   de tentar detectar mock por heurística.** Resolve dois problemas com uma
   query só: (a) identificar o que precisa reprocessar HOJE (`embedding IS
   NULL OR embedding_model IS NULL OR embedding_model <> :atual` cobre mock +
   real desatualizado + nunca semeado, sem distinguir os três — não precisa),
   e (b) operacionaliza a Regra 20 do Mestre ("trocar o modelo obriga a
   re-semear") para SEMPRE, não só hoje: troque `EMBEDDING_MODEL_NAME`, rode
   o script de novo, ele re-semeia sozinho só o que ficou pra trás — sem
   precisar zerar a coluna manualmente.
2. **HNSW em vez de IVFFlat para o índice vetorial.** IVFFlat exige uma fase
   de treino (k-means) sobre os dados já carregados para calibrar `lists` —
   é por isso que a migration 20260727120000 explicitamente não criou índice
   nenhum na época (tabela com 5 linhas, todas embedding nulo: nada para
   treinar). HNSW constrói o grafo incrementalmente, sem essa dependência, e
   dá recall melhor por padrão. Com ~637 linhas hoje (crescendo para alguns
   milhares, não milhões, no horizonte deste produto), o custo de
   build/manutenção do HNSW é irrelevante, e a vantagem que importa é não
   precisar retreinar o índice conforme o catálogo cresce.
3. **Dois bugs de correção pré-existentes, corrigidos como parte desta
   tarefa** (justificativa em "Problemas encontrados" — não são feature
   nova, são o que impedia o Critério de Aceite #3 de ser sequer testável):
   - `search-food/index.ts` não enviava `taskType`/`outputDimensionality` na
     chamada real ao Gemini — o próprio `index_test.ts` já cobria isso e
     falhava. Corrigido para bater com `extract-metric-photo/index.ts`
     (implementação já correta lá).
   - `search-food/index_test.ts` tinha um fixture (`fakeSupabaseAdmin`) sem
     `.from()`, quebrando 3 dos 15 testes ("caminho feliz" incluído) com
     `admin.from is not a function` mascarado atrás de um 500 genérico.
4. **Threshold configurável nos dois endpoints (`search-food` e
   `extract-metric-photo`), ambos com padrão 0.55.** Estavam divergentes
   (0.68 em search-food, 0.55 em extract-metric-photo) apesar do comentário
   em ambos dizendo que deveriam concordar — a divergência em si já era um
   bug de Regra 20, não uma escolha deliberada. 0.55 é o valor que o Mestre
   v7.0 já registra como aceito conscientemente (R20: risco de
   falso-positivo ocasional, mitigado por aviso de baixa confiança + edição
   manual do usuário) — mantive o valor, só o tornei configurável via secret
   em vez de constante fixa.
5. **`UPDATE` por linha em vez de `upsert` em lote na escrita do seed.**
   Tentei `upsert` em lote primeiro (1 request para N linhas) — falha porque
   `INSERT ... ON CONFLICT DO UPDATE` do PostgREST valida as constraints NOT
   NULL da linha de INSERT antes de checar o conflito, e o payload parcial
   (`id/embedding/embedding_model`) não tem `nome_taco` etc. Confirmado
   contra o banco real durante esta tarefa. O gargalo de performance real
   aqui é a API do Gemini (rate-limitada), não a escrita — `UPDATE` puro sem
   essa armadilha resolve sem precisar reintroduzir as colunas de macro só
   para satisfazer o upsert.
6. **Corrigido carregamento de `.env.local`** em `seed_food_embeddings.ts`
   (`import 'dotenv/config'` carregava só `.env`, nunca `.env.local` — onde
   `SUPABASE_SERVICE_ROLE_KEY`/`GEMINI_API_KEY` de fato vivem). Passou a
   carregar os dois, mesma convenção que o Vite já usa para o app.

## Como tratou performance (Regra 21)

- **Geração (lado Gemini)**: nada de loop ingênuo. Rate limit real via
  `EMBEDDING_RPM_LIMIT` (padrão 100 req/min → 600ms entre chamadas,
  configurável se a chave tiver um tier diferente), não um `setTimeout`
  fixo torcendo para não estourar. Retry com backoff exponencial (2s → 4s →
  8s → 16s, até 5 tentativas) em HTTP 429/5xx — só esses códigos retentam;
  4xx de configuração (texto inválido, modelo errado) falham na hora, retry
  não resolveria. Uma falha em 1 alimento não derruba a corrida inteira — a
  linha continua pendente e é pega nas próxima execução.
- **Idempotência/retomada**: a query de proveniência (`embedding_model`)
  faz qualquer execução nova processar só o que falta — não existe estado
  externo (arquivo de checkpoint) para gerenciar; o próprio banco é o
  checkpoint.
- **Escrita (lado Supabase)**: 1 `UPDATE` por linha bem-sucedida (ver
  decisão técnica #5 para por que não é batch) — não é o gargalo real; a
  API do Gemini é. ~637 UPDATEs simples neste volume são triviais para o
  Postgres.
- **Consulta em runtime (`match_alimentos`)**: índice HNSW elimina o
  sequential scan que a migration 20260727120000 deixou como pendência
  explícita — antes desta tarefa, toda busca varria a tabela inteira
  calculando distância de cosseno linha a linha.
