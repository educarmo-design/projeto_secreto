## N01 — Papéis M:N + admin único

**Não existe tabela associativa de papéis.** Busquei `create table` com "role"/"papel"/"permissao" em todas as migrations — zero resultados. O que existe é exatamente o que o spike anterior já tinha citado: `perfis_usuarios.is_admin` (boolean) + `perfis_usuarios.eh_profissional` (boolean) + `perfis_usuarios.tipo_profissional` (enum de 5 valores: `Medico`/`Nutricionista`/`Fisioterapeuta`/`Personal_Trainer`/`Auditoria_Seguradora`).

Isso **não atende M:N** no sentido literal (um usuário com múltiplos papéis simultâneos além de admin+profissional, ou um papel aplicado a múltiplos usuários via tabela própria) — é um modelo de colunas fixas. Funciona hoje porque só existem 2 dimensões de privilégio (é admin? é profissional, e de que tipo?), mas não escala para um papel novo sem uma migration `ALTER TABLE` + código nas 3 pontas (RLS, painel, tipos TS).

**"Admin único"**: fui verificar se existe uma trava de UNICIDADE (só um admin pode existir por vez). **Não existe.** `is_admin` é um boolean comum, sem `unique index`/constraint alguma limitando quantas linhas podem ter `true`. O que existe é uma trava de AUTOPROMOÇÃO (`perfis_usuarios_bloquear_auto_promocao`, trigger `BEFORE UPDATE`): nenhum usuário autenticado via API consegue setar `is_admin=true` na própria linha ou na de outro — só funciona quando `auth.uid()` é `NULL` (ou seja, uma sessão direta no Postgres/Studio, o "bootstrap manual documentado"). Ou seja: **"admin único" aqui parece significar "um único TIPO de papel administrativo" (binário, sem hierarquia), não "só pode haver um admin"** — se a intenção do fundador era a segunda leitura, isso é um gap real (qualquer operador com acesso ao Studio pode promover quantos admins quiser, sem log/aprovação de outro admin).

## N02 — Aprovação de profissional + CRN/CRM/CREF

A coluna existe: `perfis_usuarios.registro_profissional` (`text`, `20260722120000_cadastro_dinamico_campos_extra.sql`), documentada como "número do conselho (CRM/CRN/CREFITO/CREF), texto livre porque cada conselho tem formato próprio — sem validação de formato".

Duas lacunas concretas, verificadas lendo o código de ponta a ponta:

1. **O formulário de cadastro do painel nunca coleta esse campo.** `LoginPage.tsx` → `FormularioSolicitarAcesso` pede só Nome, Área de Atuação (o enum `tipoProfissional`), E-mail e Senha. Não há campo de "número do conselho" em lugar nenhum da UI de solicitação de acesso.
2. **A tela de aprovação não mostra esse campo.** `AdminDashboard.tsx` (a "Sala de Espera") faz `select('id, nome, email, tipo_profissional, criado_em')` — `registro_profissional` nem está no SELECT, muito menos na tabela renderizada. **Hoje, um Admin aprova um "Médico" sem nunca ver o CRM dele.**

Consequência prática: mesmo que alguém preenchesse `registro_profissional` via SQL direto, não há como o Admin conferir esse dado antes de aprovar — a coluna existe no schema mas está morta em toda a jornada real de aprovação.

**Cifra (D2)**: `registro_profissional` **NÃO está cifrado**. O trigger `tg_perfis_usuarios_cifrar_pii` (`20260730160000`) só toca `nome`/`telefone`/`email` — `registro_profissional` fica em texto plano na tabela. Isso é defensável (não é PII no mesmo sentido — é um dado profissional público por natureza, o CRM de um médico já é público em buscadores do próprio CFM), mas vale registrar que **não foi uma decisão documentada em lugar nenhum** — parece ter ficado de fora só porque a coluna nasceu antes do D2 e ninguém revisitou.

## N03 — Data de nascimento + idade + trava de maioridade

`data_nascimento` (`date`, nullable) existe desde a **primeira** migration (`20260706191827_core_schema.sql`) — não é algo que falte criar.

**O que não existe: nenhuma derivação de idade a partir dela.** Existe uma coluna **separada**, `idade` (`int`, `20260722120000`), autodeclarada no cadastro — o comentário da própria migration é explícito: *"não substitui... a idade calculável a partir de uma FUTURA data_nascimento real"* (grifo meu: "futura" — ou seja, os próprios autores já sabiam, em 22/07, que essa derivação ainda não existia e nunca a implementaram depois).

**Sobre a "trava ANVISA de >18 anos"**: procurei por "18 anos"/">= 18"/"maioridade"/"menor de idade" em `supabase/migrations/`, `web_painel/src/` e `lib/` inteiros — **zero ocorrências**. Não existe nenhuma validação de maioridade em lugar nenhum do código (nem client-side, nem `check constraint` no banco).

Encontrei "ANVISA" mencionado em 2 lugares do código — mas é uma regra **completamente diferente**: a "Blindagem ANVISA" (PRD Mestre §3/§5, citada em `PatientDetails.tsx` e `health_score_engine.dart`) é sobre o app de CONSUMIDOR nunca apresentar métricas cruas como "score de saúde"/"risco clínico" (para não ser regulado como dispositivo médico) — não tem nenhuma relação com idade mínima de usuário. **Se a exigência de trava de 18+ é real, ela não está documentada em nenhum PRD/Adendo que eu tenha acesso neste spike — preciso que o fundador aponte onde essa exigência está escrita, ou ela precisa ser especificada do zero.**

## N04 — Consentimento de vínculo (o domínio mais maduro)

`status_vinculo` (enum) tem **4 valores**, não 3 como o spike anterior registrou (o `database.ts` do painel está desatualizado — ver abaixo): `'ativo'`, `'em_carencia'`, `'encerrado'` (`20260713100000`) + **`'pendente'`**, adicionado depois (`20260713170000_vinculo_pendente_e_backfill_legado.sql`) especificamente para modelar o consentimento: *"Sem isto, `criar_vinculo` produziria um vínculo já ATIVO, e a RLS liberaria na hora exames, métricas e anomalias do paciente [...] sem o titular saber, ver ou poder impedir"*.

O fluxo real:

1. **Profissional convida** — o painel web **já tem essa UI**: `InvitePatientModal.tsx` + `vinculosApi.ts` chamam a Edge Function `manage-professional-link` (`supabase/functions/manage-professional-link/index.ts`) com `acao: 'criar_vinculo'` e o e-mail do paciente (não o UUID — o e-mail é resolvido server-side, já que `perfis_usuarios.email` é cifrado no cliente/D2). Isso cria um vínculo `pendente`.
2. **Paciente decide** — a Edge Function também expõe `acao: 'aceitar_vinculo'` e `acao: 'encerrar_vinculo'` (não encontrei uma ação distinta de "recusar" — recusar parece ser modelado como `encerrar_vinculo` sobre um vínculo ainda `pendente`, não confirmei o código interno da function a fundo). O lado cliente dessa ação mora no **app mobile**, não no painel: `lib/features/vinculos/data/services/manage_professional_link_gateway_service.dart` + uma tela já existente (`GerirVinculosPage`, referenciada em `configuracoes_perfil_page.dart` como "Convites de Profissionais"). Faz sentido arquiteturalmente: o convite é B2B (profissional→painel), o consentimento é B2C (paciente→app), e há até uma view dedicada (`perfis_profissionais_vinculados`, `20260713190000`) só para o app mostrar "quem está te convidando" antes do paciente decidir.
3. **Sem policy de INSERT direta** em `vinculos_profissional_paciente` para `authenticated` — de propósito, documentado: *"o vínculo é a unidade de faturamento, e o cliente não pode emitir os próprios slots"*. Toda escrita passa pela Edge Function (service role).

**Gap real encontrado, mas pequeno**: `web_painel/src/core/types/database.ts` tipa `StatusVinculo` como `'ativo' | 'em_carencia' | 'encerrado'` — **falta `'pendente'`** no union type. Isso é só uma inconsistência de tipagem (o arquivo é escrito à mão, não gerado), mas pode fazer o TypeScript não pegar um bug se algum componente novo do painel precisar renderizar/filtrar por esse status.

## N05 — Cadastro (telefone/e-mail sob D2)

Confirmado: `telefone`/`email` são cifrados pelo mesmo mecanismo D2 (`pgcrypto`, trigger `tg_perfis_usuarios_cifrar_pii`) já auditado no spike anterior.

**O painel web tem exatamente UM formulário de cadastro** — `FormularioSolicitarAcesso` em `LoginPage.tsx`, a aba "Solicitar Acesso". Os campos coletados são: Nome, Área de Atuação, E-mail, Senha. **Telefone nunca é pedido.** Não há campo, não há chamada de API que o envie — `SolicitarAcessoInput` (a interface TS em `core/supabase.ts`) nem declara essa propriedade.

Também não existe nenhuma tela de "editar meu perfil" no painel para o profissional completar isso depois do cadastro — a única leitura/escrita de perfil hoje é a auto-decifra via `meu_perfil_seguro()`, usada só para popular o nome exibido na Sidebar, nunca um formulário de edição.

## D3 — Matriz de Permissões

Não existe **nenhum artefato único** (documento, tabela de configuração, tela administrativa) que materialize "quem pode fazer o quê" de forma legível de relance. A autorização real está inteiramente distribuída em **RLS policies individuais**, uma por tabela/operação, espalhadas em **14 arquivos de migration diferentes** (contei ~65 `create policy` ao todo) + a função auxiliar `eh_admin()`.

Isso significa que hoje, para saber "um Nutricionista pode fazer X?", a única forma confiável é ler o `.sql` de cada tabela envolvida — não há como responder isso olhando para um único lugar. Para efeitos de auditoria/compliance (o que a própria tarefa D3 parece visar), isso é um gap real: a lógica está correta e bem documentada individualmente (cada policy tem comentário explicando o raciocínio), mas **não está consolidada**.
