## Parte 1 — Banco de dados

Migration `20260811240000_n09_anamnese_versionada_e_gaps_n06.sql`:

- `tipos_atividades_fisicas.met_estimado numeric(5,2)` — input do Motor N07
  (futuro, não implementado nesta tarefa); `null` até o Admin cadastrar, sem
  fonte automática.
- `problemas_saude(id uuid pk, nome text unique)` — catálogo mais simples
  que `alergias` por pedido explícito do fundador (só id + nome). RLS
  select-all-authenticated, write admin-only.
- `anamneses(id, usuario_id, profissional_id nullable, objetivo_codigo
  check in emagrecimento/manutencao/hipertrofia, data_preenchimento,
  status_vigencia check in ativo/historico default 'ativo')`. INSERT-only
  do ponto de vista do cliente — um preenchimento novo é sempre uma linha
  nova, nunca um UPDATE. RLS: dono lê/insere a própria; profissional com
  vínculo ATIVO lê (mesmo padrão de `metricas_saude_diarias`) — sem tela no
  Painel Web usando isso ainda (restrição explícita desta tarefa), mas a
  RLS já fica correta para quando existir.
- 3 tabelas N:N: `anamneses_alergias`, `anamneses_problemas_saude` (PK
  composta simples) e `anamneses_atividades` (PK composta +
  `minutos_diarios int check (> 0 and <= 1440)` — o atributo pedido pelo
  fundador). RLS própria por tabela: select (dono ou profissional
  vinculado via join em `anamneses`), insert/delete só do dono.
- **Trigger de versionamento** (`anamneses_trg_versionar`, `before insert
  on anamneses`): se o usuário já tem uma anamnese `ativo`, ela vira
  `historico` automaticamente antes do INSERT novo completar.
  `security definer` (mesmo padrão de `private.tg_perfis_usuarios_cifrar_pii`/
  `perfis_usuarios_bloquear_auto_promocao`) — necessário porque `anamneses`
  não tem policy de UPDATE para `authenticated`; sem isso a RLS bloquearia
  o próprio UPDATE do trigger. Guard `if new.status_vigencia = 'ativo'`
  evita que um INSERT que já chega como `historico` (não é o caminho do
  app hoje) apague a vigência de ninguém.

**Verificação funcional do trigger** (não só "aplicou sem erro"): script
descartável (`web_painel/scripts/_verify_trigger_anamneses.ts`, removido
depois de rodar — não é deliverável) criou um usuário de teste real via
Admin API, inseriu 2 anamneses seguidas e confirmou que a 1ª virou
`historico` e a 2ª ficou `ativo`; usuário de teste removido ao final
(cascade limpou as anamneses de teste junto). Resultado: ✅.
